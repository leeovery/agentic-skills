# Cloudflare Workers Deployment Config

How `nuxt.config.ts` interacts with Cloudflare Workers Builds + NuxtHub + D1.
The patterns here are what bite in production — read before deploying anything.

---

## Hybrid rendering via `routeRules`

Marketing pages should be prerendered to static HTML for SEO and edge-cache
hits. Private flows (forms with shared client state) should be SPA-only —
SSR adds cost with no benefit when there's no SEO case.

```typescript
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/':                { prerender: true },
    '/about':           { prerender: true },
    '/founders-letter': { prerender: true },
    '/apply':           { redirect: '/apply/fit-check' },
    '/apply/**':        { ssr: false }
  }
})
```

- `prerender: true` — generated at build time, served as static HTML from the
  Worker's asset bundle. No request hits Vue rendering.
- `ssr: false` — page renders client-side only. Form state via `useState`
  survives navigation without a hydration round-trip.
- `redirect: '...'` — static 302 at the Worker layer. Don't write `<script>`
  redirects for this; route rules are free.

Trade-off: any prerendered page that needs personalisation must escape via
`<ClientOnly>` or hydration. If 90 %+ of users see the same HTML, prerender.

## The wrangler.json binding reconciliation gotcha

`wrangler deploy` reads `.output/server/wrangler.json` (generated by Nitro's
cloudflare-module preset) and reconciles the Worker's bindings against it.

- Bindings declared in `wrangler.json` (D1, KV, ASSETS) are preserved.
- Bindings **NOT** declared there — including plain-text vars added manually
  via the Cloudflare dashboard or API — are **wiped on every deploy**.
- Secrets stored via `wrangler secret put` / dashboard "secret_text" are
  stored separately and survive.

### Rules of thumb

**Public values** (site keys, public URLs, feature flags): bake the default
into module config or `runtimeConfig.public.*` so they ship in the bundle.

```typescript
// nuxt.config.ts — public Turnstile site key (domain-restricted by Cloudflare)
turnstile: {
  siteKey: '0x4AAAAAADBtAn5zBGXm1ByI'
}
```

**Secrets** (API keys, tokens): declare under `runtimeConfig.*` with an
empty/test default; set the real value as a Worker secret once. It persists
across deploys.

```typescript
runtimeConfig: {
  resendApiKey: '',                                // Worker secret NUXT_RESEND_API_KEY
  turnstile: {
    secretKey: '1x0000000000000000000000000000000AA' // Cloudflare test secret
  }
}
```

**Runtime-overridable plain vars**: only safe if declared inside the wrangler
generator so they land in `wrangler.json` on every build.

```typescript
nitro: {
  cloudflare: {
    wrangler: {
      vars: {
        FEATURE_FLAG_FOO: 'on'
      }
    }
  }
}
```

If you find yourself adding a plain-text var via the dashboard, stop. Either
make it a secret or declare it in `nitro.cloudflare.wrangler.vars`.

## Cloudflare-module preset (NuxtHub)

`@nuxthub/core` registers the cloudflare-module Nitro preset and emits
`.output/server/wrangler.json` with:

- `main` pointing at the server entry
- `assets` binding for the prerendered HTML / static files
- `d1_databases` with `migrations_table: _hub_migrations` and
  `migrations_dir: db/migrations/sqlite/`
- Any KV / R2 / queues declared via `hub: { ... }` in nuxt.config

```typescript
hub: {
  db: {
    dialect: 'sqlite',
    connection: {
      databaseId: '1b422498-...'   // Cloudflare D1 database UUID
    }
  }
}
```

**Don't add `@nuxthub/core` to a Cloudflare project and expect it "just to
work"**: if it's missing from `modules: []`, Nitro falls back to the
`node-server` preset and `wrangler.json` is never emitted. Symptom: local
`nuxt build` succeeds but `wrangler deploy` can't find a Worker entry.

## D1 migrations are NOT applied at deploy time

`nuxt build`, `wrangler deploy`, and the Cloudflare Builds CI chain do **not**
apply migrations. Per NuxtHub docs there's no DB connection during CI, and
`wrangler deploy` doesn't run migrations either. Apply them manually from a
local checkout.

```jsonc
// package.json
"scripts": {
  "db:migrate:remote": "NITRO_PRESET=cloudflare-module nuxt build && npx wrangler d1 migrations apply DB --remote --config .output/server/wrangler.json"
}
```

Why the explicit `NITRO_PRESET=cloudflare-module`: a plain `nuxt build`
locally defaults to `node-server` and won't emit `.output/server/wrangler.json`,
so wrangler has nothing to read. The `--config` flag points wrangler at the
generated file so it uses NuxtHub's `_hub_migrations` table instead of
wrangler's default `d1_migrations`.

`npx nuxt-hub db migrate` only touches the local `.data/db/sqlite.db` — not
useful for prod.

## Build-time env vars (Cloudflare Workers Builds)

Set under **Build → Variables and Secrets**, not the runtime Worker config.

| Var | Purpose | Notes |
| --- | --- | --- |
| `NODE_VERSION` | `22` | Match local |
| `LAYER_NUXT_UI` | `github:org/repo/nuxt-ui#main` | Drives layer resolution; see nuxt-layers skill |
| `GIGET_AUTH` | GitHub fine-grained PAT | Secret. **Must be build-time, not runtime** — needed during `nuxt prepare` |

If `GIGET_AUTH` is placed at runtime scope, you'll see `Failed to download
tarball: 404` during `nuxt prepare` because `giget` can't fetch the private
layer.

## Runtime env vars (Cloudflare Worker → Settings → Variables)

Anything matching `runtimeConfig.*` can be overridden by an env var with the
`NUXT_` prefix. Nested keys use snake-case underscores.

```typescript
runtimeConfig: {
  resendApiKey: '',                  // NUXT_RESEND_API_KEY
  notifyEmail: 'apps@example.com',   // NUXT_NOTIFY_EMAIL
  turnstile: {
    secretKey: ''                    // NUXT_TURNSTILE_SECRET_KEY
  }
}
```

Set the secrets as `secret_text` (they survive deploys). Plain-text overrides
via dashboard will be wiped — see the reconciliation section above.

## Module config vs runtimeConfig: when to use which

| Pattern | Use case | Example |
| --- | --- | --- |
| `modules: [...]` config block | Module-specific public config that's safe to bundle | `turnstile: { siteKey }` |
| `runtimeConfig.*` | Server-side secrets, runtime-overridable values | `resendApiKey`, `notifyEmail` |
| `runtimeConfig.public.*` | Values needed in the client bundle, overridable per env | `apiUrl` |
| `nitro.cloudflare.wrangler.vars` | Plain-text Worker vars that must survive reconciliation | feature flags |
| Worker secret_text | High-sensitivity values, never in source | API keys, tokens |

Default values in `runtimeConfig.*` ship in the bundle, so anything there is
discoverable in the deployed Worker. Use the test/empty value as the default
and set the real value as a secret.

## Compatibility date

Bump `compatibilityDate` to the current date when creating the Worker and
keep it pinned. Nitro's compatibility date should match what Cloudflare set
on Worker creation; mismatch causes runtime divergence between local preview
and the deployed Worker.

```typescript
compatibilityDate: '2026-04-22'
```

## Common build failures

| Symptom | Cause | Fix |
| --- | --- | --- |
| `npm ci` lockfile drift | Incremental installs over a half-migrated tree | `rm -rf node_modules package-lock.json && npm install`, commit |
| `Failed to download tarball: 404` | `GIGET_AUTH` missing or at runtime scope | Move to build-time vars |
| `IPC connection closed` on `nuxt dev` | Nuxt 4 bug masks real error | Run `nuxt build` locally; real error surfaces there |
| Wrong Nitro preset | `@nuxthub/core` not in `modules` | Add it; preset auto-selects |
| Turnstile "For testing only" band in prod | Real site key not reaching client | Hardcode `turnstile.siteKey` in nuxt.config |
| `build` script becomes `tsc`, scaffold appears | WebStorm/JetBrains auto-scaffold | `git checkout -- package.json tsconfig.json .gitignore && rm -rf src` |
